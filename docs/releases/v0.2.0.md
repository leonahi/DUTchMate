# DUTchMate v0.2.0

> Published on 2026-11-28 (Europe/Paris). The
> [release workflow](https://github.com/leonahi/DUTchMate/actions/runs/46081207631)
> verified all ten public artifact filenames and SHA-256 digests on TestPyPI and
> PyPI against the same retained build artifacts.

This Python host release updates the coding-agent interface, continuous evidence
recording and Enhanced Debug Helper integration. It contains five public
distributions: `dutchmate`, `dutchmate-core`, `dutchmate-cli`, `dutchmate-service`
and `dutchmate-mcp-server`, all at **0.2.0** with exact internal dependency pins.

`dutchmate-debug-agent` is version-synchronized and tested within the workspace,
but its public distribution remains deferred. The aggregator adds no Debug Agent
dependency, extra or command.

## Installation

Requires Python 3.10 or newer. Linux and macOS are supported; Windows support is
not claimed. Install with either tool manager:

```bash
uv tool install dutchmate==0.2.0
```

```bash
pipx install dutchmate==0.2.0
```

The installation provides `dutchmate`, `dm`, `dutchmate-service` and
`dutchmate-mcp`. Locate the installed MCP launcher with:

```bash
command -v dutchmate-mcp
```

Use that absolute path in your
[coding-agent registration](../developer_guide.md#register-mcp-with-a-coding-agent).
See the [setup guide](../developer_guide.md#local-setup) for backend configuration
and the [README](../../README.md) for debugging prompts. Start the Device Core
Service before using MCP tools.

## Highlights

- **Continuous evidence:** the service records ambient UART while it owns the
  connection. Monitor and Interact use bounded windows over durable evidence;
  each operation no longer creates a separate session or physical reader.
- **Native session v2:** sessions retain connection segments, UART bytes,
  operation/action records and distinct evidence-quality dimensions. Durable
  cursors support follow/retrieval, and release/reacquire makes ownership gaps
  explicit. Recognized historical v0/v1 sessions remain read-only compatible.
- **Coding-agent tools:** the stdio MCP adapter exposes the
  [twelve-tool catalog](../specs/mcp_adapter_contract.md#target-tool-catalog),
  including Monitor, Interact, evidence retrieval and connection release/reacquire.
  MCP 2.x uses the existing thin adapter to the service.
- **Report-only DUT_VIO sensing:** compatible Enhanced helpers can provide
  voltage estimates, ADC/reference provenance and receipt age in status and
  durable evidence. Unsupported, unavailable and stale observations are explicit.
  Measurements do not change GPIO policy or populate configuration.
- **Optional voltage declaration:** Enhanced startup and GPIO control no longer
  require `hardware.dut_io_voltage`. A supplied value is still validated and
  retained as intended interface-level provenance.
- **Reliability:** queued UART evidence is committed in batches; reconnect and
  release/reacquire share the injected receipt clock; sensing startup/lifecycle,
  reconnect tests, load-profile commands and MCP launch checks are corrected.
- **Contributor workflow:** requirements/contracts live in `docs/specs/`, plans
  in `docs/plans/`, tasks in GitHub Issues/Projects and implementation evidence
  in PRs. The former development history is preserved as an archive.

## Upgrading from v0.1.0

Restart the Device Core Service with the new host after upgrading. Refresh your
coding agent's tool discovery and review scripts that use the old MCP tool names
or request shapes. Capture/wait-style MCP calls are replaced by `monitor`;
`send_uart` uses the explicit byte/text payload contract. The retired `force`
bypass and dedicated boot-test composite are absent from the target interface.
Use atomic control/observation tools to compose higher-level procedures.

The CLI provides `monitor`, `interact`, `follow`, `console`, `release` and
`reacquire`. Existing capture/wait compatibility spellings do not restore the
old per-workflow session model. Review the
[Phase 1 contract](../specs/phase1_implementation_spec.md) before migrating API
automation. Old session evidence is not rewritten into native v2.

Enhanced requires a helper compatible with the current negotiated capability
contract. The optional sensing extension reports `unsupported` when absent.
Firmware product versions and Enhanced protocol v1 remain independent of the
host version; this release does not publish versioned firmware binaries.

## Acceptance and remaining limits

Phase 1A Basic acceptance is retained. Manufactured KiCad Rev-A electrical
acceptance, Phase 1B and overall Phase 1 remain incomplete; historical EAGLE
functional evidence cannot close the current-board physical gate. See the
[milestone overview](../development_status.md) and
[board validation record](../../hardware/validation/phase1_kicad_rev_a.md).

DUT_VIO uses a documented ADC reference and reports an estimate. Lab-reference
accuracy characterization and diagnostic runtime stack measurements remain
open ([#11](https://github.com/leonahi/DUTchMate/issues/11),
[#12](https://github.com/leonahi/DUTchMate/issues/12)). Optional VS Code tool-use
and authenticated Claude Code host UI checks were unavailable, not passed
([#13](https://github.com/leonahi/DUTchMate/issues/13)). The Basic `E_COMMAND_001`
anomaly remains unresolved, unclassified and non-blocking
([#14](https://github.com/leonahi/DUTchMate/issues/14)). Debug Agent v2 packaging
and Phase 5 EVENT capture remain deferred
([#15](https://github.com/leonahi/DUTchMate/issues/15),
[#16](https://github.com/leonahi/DUTchMate/issues/16)).
